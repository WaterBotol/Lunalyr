## Packaging decision

An unpackaged, per-user installer of Lunalyr's own, not MSIX. Recorded with the reasons in
[ARCHITECTURE.md](../ARCHITECTURE.md#packaging-milestone-8); how it works in [PACKAGING.md](../PACKAGING.md). In short:
the owner can't install an unsigned MSIX at all, the app has been unpackaged and self-contained since milestone 5, it
needs no new tools or packages, and every part of it runs in tests with fakes.

- `src/Lunalyr.Install` (BCL only): the payload format (setup + zip + SHA-256 trailer, found the same way after
  Authenticode signing), the install layout `%LOCALAPPDATA%\Programs\Lunalyr\app\`, unpack-beside-then-swap with
  rollback, the registry entries (only `Software\Classes\lunalyr`, the `Uninstall\Lunalyr` key and the `Run` value
  named `Lunalyr`; any other write throws), the Start menu shortcut (source-generated COM), closing a running copy
  (`WM_APP+2` to its `Lunalyr.Host.` window, never killed), uninstall, launch at login, the update feed, Authenticode.
- `src/Lunalyr.Setup`: `Lunalyr Setup.exe`, 2.9 MB Native AOT, Windows task dialogs. Uninstall continues from a copy in
  Temp that deletes itself.
- `tools/InstallerBuilder` (make, feed, sign, verify, keygen) and `tools/Packaging/build-installer.ps1`, `sign.ps1`.
- Safety found while building: an installer renamed to `Lunalyr Setup.exe` and run with `--uninstall` from Downloads
  could have taken Downloads for the install. It now finds its install only from an `app\Lunalyr.exe` beside it, and no
  folder that doesn't hold `Lunalyr.exe` is ever replaced or removed (tests for both).

## lunalyr:// registration

`HKCU\Software\Classes\lunalyr\shell\open\command` = `"<install>\app\Lunalyr.exe" --link "%1"`, written only by the
installer and removed on uninstall only while it still opens that install. `ShellOptions` already reads everything after
`--link` as links (milestone 7); a test shows a link shaped like `--login` stays a link.

## Launch at login

The `Lunalyr` value in `HKCU\…\CurrentVersion\Run` = `"…\Lunalyr.exe" --login`; `--login` starts quietly (no settings
window, no welcome; a second launch with it opens nothing). Settings › General › Startup reads Windows' state back every
time: On, Off, turned off in Task Manager's Startup apps (a warning with **Open Startup apps**), another copy's entry (a
warning naming it), or why a write failed. `--demo` and `--data` runs never write it. The installer moves an entry for
its own install to the new app on update, and removes it on uninstall. The welcome's switch is the same one.

## Updates

Re-implemented from the Mac's behaviour: Sparkle's `AppUpdates.swift`, `UpdateConfiguration.swift` and
`UpdateConfigurationTests.swift` are all Verso lines (43/43, 20/20, 26/26), so nothing was translated; Windows has its
own tests with the same intent (feed and key both needed; insecure, credentialed and fragment feeds refused; malformed
keys refused).
- `update.json` + `update.json.sig`, ECDSA P-256 (.NET has no Ed25519). The signature is checked before the feed is
  parsed; the download must be `https`, is cut off past the feed's size, then checked for size, SHA-256, the installer's
  own payload checksum and version, and (once Lunalyr is signed) Authenticode.
- Automatic: once a day while "Check for updates automatically" is on (default on). A newer version downloads in the
  background; the HUD says it's ready once and the tray menu gets **Restart to update to Lunalyr x**. Installing runs
  the verified installer with `--update` and quits; Setup swaps the app and starts it with `--updated`, which shows
  "Updated to Lunalyr x". Old downloads are removed at start-up.
- **This build has no update service** (no feed or key built in, as nothing may be published without your OK); the
  General page says so in the Mac's words. End-to-end against a real server is untested.

### Cost per wallpaper mode

or no player (idle). Offscreen means no swap chain, Present or DWM composition, and the tool runs JIT, so CPU and memory
read a little higher than the AOT app's. Full table: [cost.md](../measurements/m8-wallpaper-cost/cost.md).

CPU is over the tool's own baseline, as a share of all 16 cores. The run ended at about 01:12, and by 01:15 the displays
had gone to sleep (see Screenshots), so they may have been asleep for part of it; offscreen drawing doesn't need them,
but the GPU's power state may differ from a lit desktop. Live numbers from the AOT app on the desktop (`--stats`) need
the wallpaper drawn on your screen, so they wait for your OK. Every mode held 60 fps (a few runs missed 16–27 of
~900 slots). Private memory is about 100–350 MB over the baseline, highest with video. Two things worth a look later:
- Silk is the heaviest by far on the Intel GPU (12 ms a frame, three quarters of it busy, even idle). The Performance
  page's power tiers step heavy effects down on battery; Silk at full rate on AC may still be too much for an iGPU.
- The lyric layers allocate a little on every playing frame (median 40 B, bursts to ~20 KB when a line is set). Earlier
  milestones' allocation tests cover a line once set; this is the setting of new lines. Not a problem at this size.

Idle with nothing on screen: Test Build 7 itself (the owner's copy, the tray and its wallpaper) wasn't measured, as it is
the owner's running process.

## Flaky tests

Fixed by cause, no retries, skips or longer timeouts (branch `m8/flaky-tests`; fuller notes in the commits):

| Test | Cause | Fix | Runs failed, before → after |
|---|---|---|---|
| `MusicVideoLayerTests.ReduceMotionHoldsTheFirstFrameShown` | **App race:** Reduce Motion held whatever frame showed first; after a seek a slow decoder hands over the frame just before the target first | Hold the video *time*, so the still settles on its own frame; new test fails every time on the old code | 1/30 → 0/100 |
| `WallpaperTypesTests` "MatchTheMusic…" | Test read the renderer before the lookup handed the wallpaper over | Wait for the controller to be idle first | 4/40 → 0/130 |
| `MotionCoverTests` | **App race:** seven places worked out the layers and handed them over later with nothing ordering them, so an older wallpaper could replace the animated cover and stay; plus an early read like the one above | `PublishLayers()` under one lock (as `PublishScene` does); new test fails 3/3 on the old code | 2/50 → 0/130 |
| `ScatteredFamilyRenderTests` allocation check (and other offscreen comparisons) | Offscreen frames got 2.5 ms of *real time* to set lines ahead, so the state compared depended on machine load | Offscreen work ahead of time is always allowed (as `FrameContext.AheadWork` already said); the desktop's pacing is unchanged; new test fails 31/32 cases on the old code | 6/20 → 0/45 |
| `SpreadSetupRenderTests` (portal, mosaic) | Inferred from one instrumented failure: the reference layer, drawn again at the same moment on the same hardware device while another process used the GPU, didn't reproduce its own frame (1 pixel off by 126/255). The test's logic is deterministic | The comparison runs on WARP, Direct2D's software rasteriser, where the same input always draws the same pixels (36 s for the class). It no longer covers the hardware path; the render tests that aren't pixel comparisons still do | ~1/20–50 → 0/15 under GPU load |
| `ReduceMotionRenderTests` (mosaic) | Never reproduced in ~70 runs, so unproven. It compares exact pixels on the hardware GPU, the same exposure as above, and the wall-clock budget above could also explain it | Moved to WARP as well | – → 0/10 |

Side effect of the offscreen fix: the settings preview and lyric cards set a laid-out line whole on the next frame
instead of over several.
